# 体力消耗埋点口径

最近验证状态以 `gravity sql status --json` 解析出的 immutable snapshot 及其 `energy-profile-coverage` 为准，输出必须保留 snapshot ID 与 hash；代码事实只作为字段来源说明。

## 可执行查询

```powershell
gravity sql status [--json]
gravity sql verify [--date YYYY-MM-DD] [--publish]
gravity sql query energy-profile-coverage --start YYYY-MM-DDTHH:MM:SS --end YYYY-MM-DDTHH:MM:SS [--app-id ID ...]
```

该产品只验证 `total_usepower_num`、`total_getpower_num` 和 `current_power` 用户属性快照的覆盖情况，不计算或声称窗口内体力消耗。`AssetList` 只作诊断信号，缺失不会单独阻断产品。返回 `partial` 时必须保留 `warnings` 和 `forbidden_claims`；`stale`、`pending_review` 或 `blocked` 时拒绝查询。只有显式 `verify --publish` 才更新最近验证证据。

## 结论

代码中“体力”对应 `power` / `AssetsType.Energy` / 资源 `id=2`，且没有逐次体力消耗事件；分析应使用汇总/快照口径，不能用 `paid_assets` 逐次还原。当前可用性必须读取最近验证证据。

命名陷阱：`energytrain` 是能量列车礼包活动积分，不是体力消耗。

## 候选查询口径

| 口径 | 用途 | 限制 |
|---|---|---|
| 用户属性 `total_usepower_num` | 查累计体力消耗 | 是用户属性，不在 `default.event.properties` 事件流里 |
| 用户属性 `total_getpower_num` | 查累计体力获得 | 同上 |
| 用户属性 `current_power` | 查当前体力快照 | 同上 |
| `AssetList.asstes_2` | 事件侧当前体力快照 | 2026-06-01 至 2026-06-12 的 SQL 核验未命中 `AssetList` |
| `AssetList.asstes_9` | 事件侧累计体力消耗快照 | 同上，需先排查事件为什么未入库或不可查 |
| `power_multipe` | 体力倍率切换行为 | 只说明切倍，不等于消耗量 |
| `generator_get` | 棋盘深度代理 | 不能直接换算体力消耗 |
| `paid_assets_type=2` | 体力获得 | 只能看产出，不能看发射器扣体力 |

## 分析使用规则

- 做资源产耗时，金币、钻石、材料可以用 `paid_assets_get/use` 计算产耗；体力不能这样算。
- `energy-profile-coverage` 只报告快照字段覆盖率；单个窗口里的累计值不是窗口消耗量。
- 如需计算体力消耗，必须另行取得同一用户在窗口两端的可比快照，并处理重置、封顶和上报延迟；本产品不提供该结论。
- 如果只查 `default.event`，应写成“事件流未命中体力消耗”，不要写成“没有体力消耗数据”。
- 不建议全量新增逐次扣体力事件，发射器点击频率高，容易造成事件量膨胀；更稳的是修通用户属性看板或排查 `AssetList`。
- 埋点表和看板中应把 `energytrain` 归到礼包活动，不要归到体力资源。
