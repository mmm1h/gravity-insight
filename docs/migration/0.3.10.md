# Migrating to 0.3.10

## Startup Updates: Hard Break

Previously an unset `GRAVITY_INSIGHT_AUTO_UPGRADE` disabled release checks;
enabling it produced an external Installer plan but installed nothing. Now an
unset value enables real pip installation and a supervised re-exec before CLI
command dispatch. This changes consent to network access, disk writes and code
execution, so it is a Hard break, not an additive notification change.

The Owner-selected startup policy installs newer stable releases **including
Hard breaks**, without compatibility-based skipping. The external Installer's
`gravity.release-compatibility.v1` policy remains available to separately
managed consumers; it is not the CLI startup decision procedure.

For manual lifecycle control, explicitly configure:

```powershell
$env:GRAVITY_INSIGHT_AUTO_UPGRADE = "0"
```

`false`, `no`, and `off` are also accepted, case-insensitively. This stops both
checking and staged-version activation, leaving the base installed runtime in
use. An exact `GRAVITY_INSIGHT_PINNED_VERSION` matching the base running version
also disables startup updates. Doctor and existing test/evaluation off switches
remain effective. Existing legacy environment fallbacks retain primary-name
precedence. There is no plan to remove the explicit off switch.

Without migration, CLI startup can execute a newer breaking version. API-only
Python imports do not auto-install or switch versions. `--help` remains a normal
startup command; use the explicit off switch for offline help.

## Obtaining This Version

Startup updates cannot deliver themselves. The code that performs them ships
*in* this release, so a runtime on 0.3.9 or earlier has nothing to run and will
not arrive here on its own. Install once by hand:

```powershell
pip install --upgrade gravity-insight
```

From 0.3.11 onward an enabled runtime follows releases without intervention.
Consumers who do not want that must set the off switch **before** running any
0.3.10 command: the first startup after this upgrade is already governed by the
new default, so setting it afterwards can come one release too late.

## Installation and Activation

`target_python` or `GRAVITY_INSIGHT_AUTO_UPGRADE_TARGET_PYTHON` selects the
interpreter; absent configuration uses the current interpreter. Pip installs
the exact detected release and dependencies with `--only-binary=:all:` into a
unique cache stage. Missing compatible wheels are a nonfatal update failure.
No pip uninstall/upgrade modifies the already imported package or dependencies.

Stages live below `update_state_path().parent/runtime-updates/<target-scope>/`.
The existing OS-backed lease primitive holds a target-scoped lock across pip,
isolated version/import verification and atomic publication. A busy startup
continues on the base version. Published stages are never overwritten; future
enabled CLI startups reuse the stage and the 24-hour release-check cache.

After verification, a fresh Python child receives the original command args,
cwd, stdio, environment and selected workspace. Its updates are disabled to
prevent recursion. The waiting launcher returns the child's business exit code
and never replays that command on the old version. This is supervised re-exec,
not in-process module replacement. Direct callers of `maybe_auto_upgrade` get
an installation receipt; their current interpreter remains on its old version.

Check/pip/preflight failure is a Soft break in error handling: instead of
exit 75, stderr gives a reason and next action and the base command continues.
Failed installation attempts back off for 24 hours; successful release checks
still use `update-check` state. Failed network checks are not cached as success.
Read private `pip-*.log` files for pip's detailed reason. Do not publish these
logs: configured package indexes can expose credentials in diagnostics.

## Machine-Readable Context

`gravity.runtime-update-receipt.v1` records are separate from measurements:
they describe a lifecycle transition, not a measured business value. Records
include `from_version`, `to_version`, UTC `captured_at`, `trigger.kind` and PID,
`target_python`, `stage`, `running_version`, `status`, and `receipt_id`.
Installation receipts say `installed`, not activated. Activation records start
as `activation_requested` and end as `process_exited` with the child's exit code;
an interrupted launcher may leave the former and must not be counted as proof
of successful execution. The child receives the path through
`GRAVITY_INSIGHT_UPDATE_RECEIPT`; capture it with analysis provenance to bind
results to the runtime used. Business argv and usernames are not recorded.

The base environment remains available for opt-out/failure recovery. Stages and
failed-attempt evidence are retained, not automatically garbage-collected.
Remove obsolete stages only when no process is using them. Global `pip show`
continues to describe the base installation, not the selected isolated stage.
