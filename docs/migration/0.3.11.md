# Migrating to 0.3.11

## User Detail Aggregate diagnostics: Hard break

**受影响**：按 `user-detail-aggregate` 错误码或 `category` 分支的 CLI、SDK、Plan 与 Agent 消费方，
尤其是把所有 `category=upstream` 都交给上游修复或等待重试的调用方。

| 失败原因 | 旧诊断 | 新诊断 |
|---|---|---|
| 字段被 user-detail 隐私策略排除 | `USER_DETAIL_AGGREGATE_FIELD_UNSUPPORTED`, `caller`, exit 2 | `USER_DETAIL_AGGREGATE_FIELD_PRIVACY_EXCLUDED`, `caller`, exit 2 |
| 条件非空取值类型集合与本次实测的非空、单一行类型不符 | `USER_DETAIL_AGGREGATE_MIXED_TYPE`, `upstream`, exit 3 | `USER_DETAIL_AGGREGATE_CONDITION_TYPE_MISMATCH`, `caller`, exit 2 |
| 实测行自身混型、非标量，或登记数值字段返回非数值 | `USER_DETAIL_AGGREGATE_MIXED_TYPE`, `upstream`, exit 3 | 不变 |

隐私错误继续使用值无关的通用诊断，不暴露被保护字段名、App 标识或源值：

```text
USER_DETAIL_AGGREGATE_FIELD_PRIVACY_EXCLUDED
message: aggregate field is excluded by the user-detail privacy policy
field: fields
next_action: Remove the field or switch to an owner-approved privacy-governed product; type registration cannot make a privacy-excluded field eligible.

```

条件类型错误则改成精确、安全的定位信息。假设第 9 个 measure `ad_cid_coverage` 对字符串字段
`AdCid` 同时给了 string/number 条件，诊断为：

```text
USER_DETAIL_AGGREGATE_CONDITION_TYPE_MISMATCH
message: aggregate condition for measure 'ad_cid_coverage' on field 'AdCid' uses non-null value types number, string; observed field type is string
field: measures[8].condition.values
next_action: Use only string condition values for field 'AdCid' in measures[8].condition.values, or remove that condition; do not retry the unchanged request. Investigate upstream only if separate type-drift evidence exists.
```

顶层 filter 使用同一格式，`field` 为 `filters[i].values`。message 只包含调用方已提交且已通过
字段隐私资格校验的 measure/字段名和标量类型，不包含条件实际取值、App 标识或用户行。

两条新诊断均为 `category=caller`、`retryable=false`。旧条件类型分支本来也返回
`retryable=false`，所以遵循该字段的消费方不会增加或减少自动重试；按 `category=upstream` 自行等待、告警或派给
上游 owner 的消费方，以及按 exit 3 分支的 CLI 编排，都必须改按新 code/exit 2 处理并提示调用者收窄条件类型。隐私分支必须删除字段或改走 owner 批准的
隐私治理产品；补字段类型登记不会解除策略排除。

**不迁移的后果**：精确匹配旧 code 的调用方会把新错误落入 unknown；按 category 分派的调用方会继续把条件输入问题
误派给上游。**旧写法本次即移除，无过渡别名**，因为同码同时表达策略排除与类型未登记，或让同一个 mixed-type code
同时表达 caller 与 upstream，都会使 Agent 无法机器决定下一步。

除下述 `bytedanceMid1..8` 误排除外，拒绝集合、请求顺序和隐私规则均未放宽；真实混型仍使用原
code。条件 `NOT_IN [null, "", 0, "0"]` 这类跨物理类型表达仍会被拒绝，本次不放宽检查。

## User Detail Aggregate material-field eligibility

`bytedanceMid1..8` 不再仅因 `bytedancemid` 前缀被 `user-detail-aggregate` 排除；字段仍须存在于
contracted 顶层标量或 live user-property metadata，且只能经过现有有界聚合链路输出 group/cell。
`_DIRECT_IDENTIFIERS`、direct-personal response policy 与 credential/session policy 不变，用户行、
用户 ID 和设备 ID 仍不进入结果。

当前[公开 Gravity 用户数据字典](https://help.gravity-engine.com/docs/user-data-dictionary)明确把 `Mid1..6`
定义为图片、标题、视频、试玩、落地页和安卓下载
详情页 ID；仓库没有 `Mid7/8` 的精确子类型证据。后两者也只恢复物理聚合能力，不替调用项目
猜业务名称。

## `WITH_VAL` non-null semantics

运行语义不变：`WITH_VAL` 判断 JSON 非 `null`，所以 `""`、`0` 与 `false` 都算有值；缺失字段按
`null` 处理。该事实现在写入 `--input-schema`。字符串字段需要“非 null 且非空”时，在顶层 filters
中组合：

```json
[
  {"field":"AdCid","operator":"WITH_VAL","values":[]},
  {"field":"AdCid","operator":"NOT_EQUALS","values":[""]}
]
```

若字段另以 `"0"` 表示业务空值，可再使用同为 string 的 `NOT_EQUALS ["0"]` 或
`NOT_IN ["", "0"]`；不要把数值 `0` 混入 string 条件。没有新增操作符，也没有把 field-specific
sentinel 猜成全局“空值”。

## Model claim policy: Hard break

**受影响**：读取 `gravity_insight/contracts/models/*.json` 的 `claim_policy` 并按字符串匹配的消费方。

**旧 → 新**（三档全部改为规范稳定 ID）：

| tier | 旧 | 新 |
|---|---|---|
| `validated` | `deterministic scenario over caller-bound parameters` | `deterministic-scenario-over-caller-bound-parameters` |
| `scenario` | `unvalidated project calibration scenario` | `unvalidated-project-calibration-scenario` |
| `forbidden` | `causal claim` | `causality` |
| `forbidden` | `project accuracy guarantee` | `project-accuracy-guarantee` |
| `forbidden` | `guaranteed future outcome` | `guaranteed-future-outcome` |

`causality` 复用 Skill/Journey 已有 ID。其余四个没有精确上层对应物，保留为独立 ID，
不用更宽或更窄的近义约束代替——合并两个范围不同的约束会静默放宽其中一个。

**不迁移的后果**：匹配旧字符串不再命中。**漏匹配 `forbidden` 不会报错**，读起来是
"未被禁止"，于是调用方会开始放行一条它以前拒绝的因果断言，全程静默。按安全相关变更处理。

**迁移**：把 `claim_policy` 的值当作不透明 ID 按精确值比较。**不保留自然语言别名，
今后也不会加**——别名表会把这次消除的歧义重新引入。需要展示文案的，映射放在自己的展示层。

**旧写法移除计划**：本次即移除，无过渡期。`models describe`/`evaluate` 的字段形状、
模型 URI、审批选择逻辑与全部数据读取能力均未改变。

## 门禁

`scripts/check_skill_journey_contracts.py` 现覆盖 Model 层，两个 fail-closed 判据：
`model-claim-id-invalid`（不是规范 ID，例如仍带空格）、`model-claim-id-unknown`
（格式合法但未登记）。后者才使它不只是格式规则——凭空造的合法 ID 同样失败。

## Capability Validation evidence v2

**受影响**：直接读取私有 Capability Validation run/summary JSON，按 v1
`schema_version` 分支，或固定读取
`agent-runtime/capability-validation-summary.v1.json` 的维护工具。

新采集的 run 使用 `gravity.capability-validation-run.v2`；离线汇总使用
`gravity.capability-validation-summary.v2`，写到
`agent-runtime/capability-validation-summary.v2.json`。每个 outcome 新增两个可选诊断：

```json
{
  "response_drift": {
    "schema_version": "gravity.response-drift.v1",
    "direction": "response",
    "classification": "additive",
    "fields": [{"path": "/data/new_field", "observed_type": "string"}]
  },
  "error_detail": {
    "code": "CONTRACT_CHANGED",
    "category": "upstream"
  }
}
```

`response_drift` 只包含规范化 JSON Pointer 和 JSON 类型；`error_detail` 只包含 Runtime
已知机器错误码以及 `caller/upstream/local/unknown` 分类。响应值、错误消息、错误 field、
`next_action`、异常文本和 unsupported item 均不持久化。

汇总器继续读取已有的 v1 run，历史 outcome 没有诊断时保持字段缺失，不伪造也不要求重跑。
它只生成 v2 summary，不继续双写 v1 文件；否则两个文件都会看起来像当前权威摘要。未迁移的
严格 v1 parser 会拒绝 v2，固定读取旧文件名的工具会停留在旧证据。迁移时改读 v2 文件、按
v2 schema 校验，并把两个诊断字段视为可选：旧 run 无法补回从未保存的明细。

此次版本升级不删除采集、离线汇总、历史 run 读取或 Trust 判定能力；`summarize` 命令返回的
计数形状保持不变。回滚时必须同时恢复 run/summary schema version、summary 文件名和 outcome
形状，不能只恢复旧文件名。

## Capability completeness requirements: Hard break

**受影响**：断言 `journey can-run` / `capability` 拒绝原因为 `COMPLETENESS_INSUFFICIENT`
的消费方，以及读取三个 claim-bearing Capability 合同里 `completeness` 要求值的工具。

三个 claim-bearing Capability 合同不再要求不分页的 dependency 提供
`completeness: "complete"`。这四个 operation 声明 `pagination.kind: "none"`，而
completeness 词表（`unknown`/`prefix`/`complete`）的升级判据完全建立在末页回显与总数
一致上，因此它们的排名**永远不可能**高于 `unknown`。结果是每个 claim-bearing capability
被永久拦住，运行时发布空的 `allowed_claims`——证据早已采到（`pagination_evidence` 已是
`production`），答案本身就是 `unknown`，"再去采证据"是条死路。

修法不是放宽判定，而是让要求强度与 claim 语义对齐：`returned-*`、`selected-*`、
`window-*` 这些 claim 本来就没有声称完整性，逐个 dependency 下调即可。
`report.business.query` 确实分页，继续要求 `complete`。

**旧写法**：受影响 Journey 的 `can-run` 返回 `COMPLETENESS_INSUFFICIENT`。

**新写法**：缺少 Validation Result 的 dependency 报
`DEPENDENCY_VALIDATION_UNKNOWN`——**跑一次验证就能解决**，而不是按合同永远无解。

**不迁移的结果**：按旧错误码分支的调用方拿不到匹配，会把"待验证"误读成"未拦截"。

`meets_completeness`、`assess_capability_requirement` 与 `COMPLETENESS_INSUFFICIENT`
拒绝本身均未改动。新增 CI 门禁 `claim-dependency-requirement-unreachable`：任何
claim-bearing capability 声明了 dependency 永远无法满足的要求，构建即失败。

## Response projection reconciliation: Hard break

**受影响**：严格解析响应或 `describe` 输出的 parser、依赖 additive
`result_audit.response_drift` 驱动自动化的工具，以及依赖旧省略策略的调用方。

22 个 stable operation 的响应投影与上游实际返回对齐了。三类变化：

1. **原先省略的字段现在会被投影**——同一响应不再产生 additive drift，而是多出字段。
2. **新增 known-omitted 声明**——同一响应不再产生原先的 additive drift，字段仍不输出。
3. **部分 JSON 容器字段改为 opaque 接受**——原先会被拒绝，现在原样透传（其内部键受
   递归隐私排除与规模上界约束，见下节）。

`contract_version` 未随之提升。Validation Result 的失效由 `contract_digest`
负责——它经 `contract_fingerprint` 覆盖 `response_projection`，投影一变摘要即变，
陈旧证据会被判 `CAPABILITY_FINGERPRINT_MISMATCH` 隔离，因此不存在证据静默沿用。

## Opaque JSON containers: 递归隐私排除与规模上界

`opaque_json_item_keys` 声明的字段原样透传上游嵌套 JSON。此前其内部键既不参与字段级
隐私策略，也不被最终脱敏——上游返回 `album_authority={"user_ids":[991],"email":"..."}`
时 `email` 会直达输出，且 `drift=0`、无 warning。

现在容器内部**递归**适用与顶层相同的键级排除（直接个人标识、敏感分析字段、
credential 名与后缀），并受三重上界约束：32 KB 序列化字节、深度 8、256 个元素。
超限的容器判为 breaking drift 而非静默截断。

这不改变 opaque 的用途：无法预先声明形状的上游 JSON 仍然透传，只是不再是策略盲区。

## Structured JSON input error classification: Hard break

**受影响**：按 `--input` 失败的错误码、category 或退出码分支的 CLI 与 SDK 调用方
（`agent`、`plan`、`analysis query`、`derive`、`export` 等共享同一份解析）。

| 输入 | 旧 | 新 |
| --- | --- | --- |
| 不存在的路径、`metadata:search` 这类裸 selector 字符串 | `LOCAL_IO_ERROR` / exit 4 | `INPUT_INVALID` / `category=caller` / `field=input` / exit 2 |
| 非 UTF-8 的文件或标准输入 | `INPUT_INVALID` / exit 2 | `LOCAL_IO_ERROR` / `category=local` / `field=input` / exit 4 |
| 畸形 JSON | `INPUT_INVALID`，`field=null`，无恢复动作 | `INPUT_INVALID`，`field=input`，附 `next_action` |

`export` 另外开始优先保留异常自带的 `next_action`。两类失败的可重试性均未改变。

## General read response drift v2: Hard break

**受影响**：严格按 `gravity.response-drift.v1` 解析 drift 的 parser，以及拿
`response_drift.SCHEMA_VERSION` 去校验所有 drift 产物的调用方。

这一条**独立于** Capability Validation evidence v2：普通 `read()`、receipt 与
result audit 同样会产出新结构。

- breaking drift 使用 `gravity.response-drift.v2`；**additive-only 仍是 v1**
- 每个 field 新增 `classification`；breaking field 另有 `expected_type`
- `observed_type` 新增 `missing`、`non_json`
- 导出的 `response_drift.SCHEMA_VERSION` 现指 v2

因此"拿 `SCHEMA_VERSION` 比对每一份 drift"这种写法会在 additive 产物上失配。正确做法是
按每份产物自己的 `schema_version` 分支，并用 `classification` 决定处置。

## `evaluate_playbook_data_quality()` signature: Hard break

**受影响**：直接调用该公开函数（在 `__all__` 中）的 Python 调用方，以及严格解析其
返回的 DQ `checks` 数组的消费方。

- 删除必填的 keyword-only 参数 `completeness=`；按 0.3.10 的写法调用会抛 `TypeError`
- 返回的 `checks` 不再包含 `completeness` 项，也不再产生 `DATA_QUALITY_UNPROVEN`

completeness 现在与数据质量分开评估——这正是上面第一节那条 Hard break 的落地形式。
