# Migrating to 0.3.27

## User-event export task scope

`export.analysis.user_event.start` now captures the exact caller request and its
metadata-backed event identities before creating one task. `export run` carries
that frozen scope through polling and verifies the workbook's client, inclusive
file-timestamp dates and selected event basket before atomic publication. The
scope check preserves every occurrence, including equal timestamps. It neither
trims wrong rows nor retries task creation to obtain a different file.

For staged execution, retain the `completeness` object returned by the original
`export start` (or a run error that established an exact recoverable task). Save
that object alone as a private JSON receipt, then supply it on download:

```powershell
gravity export download <job-id> --operation-id export.analysis.user_event.start --completeness <receipt.json> --output <file>
```

SDK callers pass the same object as `export_download(..., completeness=receipt)`.
The task identity and request fingerprint must match; another task's receipt,
a modified receipt or a missing receipt fails before download. Keep the receipt
private: dates and registered event aliases describe the caller's scope. Client
and request values use salted fingerprints. Its checksum detects accidental
drift; it is not an authenticated signature or an upstream scope attestation.

Legacy tasks without a comparable original receipt cannot be certified by this
path. Keep their files quarantined, inspect existing tasks, and use registered
native projected reads with explicit scope/coverage controls when necessary.
There is no bypass mode or automatic re-create after an uncertain or semantically
rejected start. All current create parameters, authorized fields and raw native
read capabilities remain available. The canonical work-dashboard code has no
consumer requiring migration; frozen reports retain their historical commands.

## File completion and source evidence

`completion_status=complete` or `empty` describes the verified file transfer.
User-event `obligations.data_completeness` remains `unknown`; the separate
`completeness` object exposes file scope verification and unavailable native
snapshot/as-of/reconciliation evidence. A later workbook need not be the same
content vintage as an earlier native summary. Do not overwrite the old summary,
delete extra rows, deduplicate tied events or fill missing events as zero.

The registered file has no App column and cannot certify every user/property
condition. Those limitations remain explicit. Dates are checked in the calendar
written in each file timestamp, without inventing a timezone conversion or native
financial-day guarantee. Event display names are accepted only when governed
metadata maps them unambiguously; unknown or ambiguous identities fail closed.

## Realtime diagnostic scope and result v2

`analysis.realtime_event.list` uses contract v2, and the bounded product returns
`gravity-insight.realtime-event-catalog.v2`. Keep the explicit Asia/Shanghai
`YYYY-MM-DD HH:MM:SS` start/end window within24 hours. Only page1 is accepted;
the upstream page-size control does not establish paging or content closure.
At most1000 returned rows are accepted, with the cap observation kept separate
from `obligations.data_completeness=unknown`. Empty means no rows were returned
for this call; it does not prove that the SDK sent no events.

The existing CLI route and SDK method remain:

```powershell
gravity analysis realtime-events --app <alias> --start "<local-start>" --end "<local-end>" --event-name <metadata-name> --client-lib <sdk> --client-lib-version <version>
```

Ordinary event/SDK/version/type/client/request filters combine with AND. The
default event type remains `profile`; use an explicit empty string to omit
that filter. Registered client/request identifiers remain available. Identifier
and property-condition values remain redacted from request echoes; the product
scope preserves the safe event/type/SDK/version filters used for the observation.

Use at most one `properties` condition with exactly `field`, `datatype`,
`operator=EQUALS` and one scalar in `values`. The field/type must match same-App
metadata. Extra filters/values and unverified LIST/DICT comparisons fail before
the target read. SDK/Plan callers select up to20 scalar metadata names with
`property_fields`; CLI callers repeat `--property-field` and may supply one
JSON/file `--property-filter`. Selected output includes per-property coverage;
missing values remain unavailable. Raw property objects, credential/identifying
attributes, IP and UA are not published through this surface.

Plan accepts only the v2 product with its typed obligations and closed diagnostic
scope. Update custom result decoders to v2; old or inconsistent envelopes fail closed.
The current canonical work-dashboard consumer has only route/help checks and
generic start/end examples, so no v1 result decoder requires migration. The
existing bounded profile request, original projected identifiers and other read
families remain available. SDK/version nonempty equivalence and the real MCP
Host/holdout/adopter receipts remain separate acceptance gaps; this change does
not certify complete official MCP replacement or graduate its experimental host.
