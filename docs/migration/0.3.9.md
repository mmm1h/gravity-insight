# 迁移到 0.3.9

## 上游/内部故障不再归类为调用方输入错误

五个 raise 点此前把**上游返回**或 **Runtime 内部合同**的问题报成
`INPUT_INVALID / caller / field=<某个调用方输入字段>`，退出码 `2`。调用方据此
去检查自己的输入，但问题不在输入里，改什么都修不好。

现在它们返回 `CONTRACT_CHANGED / upstream / field=null`，退出码 `3`：

| 触发条件 | 改前 | 改后 |
|---|---|---|
| operation 输出不是对象 | `INPUT_INVALID` `field=result` | `CONTRACT_CHANGED` `field=null` |
| operation schema 不是对象 | `INPUT_INVALID` `field=schema` | `CONTRACT_CHANGED` `field=null` |
| schema 缺 `response_projection` | `INPUT_INVALID` `field=schema` | `CONTRACT_CHANGED` `field=null` |
| Multidim 产品 schema 无效 | `INPUT_INVALID` `field=name` | `CONTRACT_CHANGED` `field=null` |
| schema 缺动态绑定字段（原为裸 `KeyError`） | `INPUT_INVALID` | `CONTRACT_CHANGED` |

**消费方要改三处：**

1. **退出码**：对这些路径按 `2` 分支的脚本改为识别 `3`。成功路径与其它错误码的
   退出码没有变化。
2. **异常类型**：`ContractChangedError` **不是** `ValueError` 的子类，而
   `InputValidationError` 是。只 `except ValueError` 的处理器不再捕获它们。
   两者都在 `GravityInsightError` 之下，捕获该基类的代码不受影响。
3. **不要再读 `field`**：这些错误的 `field` 现在是 `null`。此前那个值指向一个
   调用方输入字段，是错的——它是本次修复的对象，不是可依赖的契约。

错误 `message` 文本没有变化，所以按消息匹配的代码不受影响（但不建议这么做）。

## `next_action` 现在给出修复主体与停止条件

这些错误的 `next_action` 此前是一句通用的「运行 `operations describe` 并按文档重
试」，对拿到错误的一方不可执行。现在它给出三件事：**谁该修**、**下一步做什么**、
**什么时候该停止重试**。例如 Multidim 产品 schema 无效时：

```
Repair owner: Gravity Runtime Multidim contract maintainer.
Next step: repair and republish the multidim_input_schema properties contract.
Alternative selector: `report.multidim.query` remains an expert raw-operation
route after `gravity agent-catalog describe report.multidim.query`; it is not
product-equivalent.
Stop condition: do not retry `composite:multidim` until the product schema is
re-verified.
```

`operation output must be an object` 一例的 repair owner 标为
**`undetermined`**——在那一层无法区分是上游真的变形了，还是 Runtime 的合同过期
了。这是有意为之：归错 owner 比不写 owner 更糟，而那正是本次修复的病因。自动化
消费方遇到 `undetermined` 应把证据上交人工判断，不要自行选一方重试。

**替代 selector 不保证可用。** `report.multidim.query` 只是一条已验证可解析的专
家 raw-operation 路径，与产品路径不等价；如果根因同时影响上游，它也会失败。
