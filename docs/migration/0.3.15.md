# Migrating to 0.3.15

## Exact Runtime Pins: Hard Break

Affected consumers set `GRAVITY_INSIGHT_PINNED_VERSION` or its legacy fallback
`GRAVITY_SDK_PINNED_VERSION`. Previously only a pin matching the imported runtime
disabled updates; malformed and mismatched pins silently allowed latest checks
and execution of another version. That permissive behavior is removed in 0.3.15,
with no compatibility mode. Default team auto-update policy is unchanged.

The enforced startup path is `gravity` / `python -m gravity_insight` and the
startup helper APIs. Standalone `gravity-insight` and `gravity-sql` scripts
currently bypass the shared startup lifecycle; use `gravity insight` and
`gravity sql` for pin enforcement. Wiring those separate entry points needs
a separately approved scope extension.

| Effective pin / configuration | Startup outcome |
| --- | --- |
| Exact imported version (e.g. 0.3.15) | Updates disabled; run this version |
| Other stable X.Y.Z (e.g. 0.3.11 or 99.0.0) | Reject with RUNTIME_PIN_MISMATCH, caller exit 2 |
| Invalid format | Reject with INPUT_INVALID, caller exit 2 |
| Empty, whitespace or unset | Default-on updates |
| Empty/unset pin plus explicit update off | Run imported version without updates |
| Invalid/mismatched pin plus explicit update off | Still reject |
| Target Python configured | Does not override the current process's pin |
| Offline | Same pin decisions; without pin, failed update check is nonfatal |

Surrounding pin whitespace is stripped; the stable three-component grammar is
unchanged. A present primary variable wins over the legacy variable even when
empty; legacy update/target-Python fallbacks retain their existing precedence.
Doctor, cache, help and dry-run commands cannot bypass a nonempty pin. Doctor and
cache remain update-offline after pin validation. API imports alone do not run
startup validation; `startup_update_enabled` and `maybe_auto_upgrade` raise the
structured errors instead of returning enabled for an invalid execution pin.

## Migration and Remedy

Set the intended pin before the first command. For malformed input, correct the
format. For a mismatch, explicitly provision the exact version into an intended
environment with supported Python 3.11/3.12 and invoke that interpreter; merely
setting `GRAVITY_INSIGHT_AUTO_UPGRADE_TARGET_PYTHON` cannot switch the currently
imported runtime to satisfy the pin. For example, outside a source checkout:

```powershell
& $targetPython -m pip install "gravity-insight==$exactVersion"
$env:GRAVITY_INSIGHT_PINNED_VERSION = $exactVersion
& $targetPython -m gravity_insight --help
```

This is manual guidance, not an automatic installer invocation. If the exact
version is unavailable, stop and confirm the intended version; never substitute
latest. Without migration these commands now fail before distribution calls,
authentication, Skill maintenance or business dispatch. Deliberately clearing
the pin returns to the default team update policy. Neither refusal nor remedy
automatically rewrites a project lock. No existing read capability is removed.

## Execution Version Evidence

Installation remains an immutable stage followed by a fresh supervised child.
An installation receipt's `running_version` describes the installer process,
not activation. In `gravity.runtime-update-receipt.v1` activation records,
`running_version` is now nullable: `activation_requested` starts with null.
The child verifies its import is inside the stage and its imported `__version__`
matches the requested target, then atomically records `process_started` and that
observed version before invoking the CLI. The parent preserves the observation
and records `process_exited` plus exit code. A missing observation remains null,
even when a child exits; readers must not substitute `to_version` or `pip show`.
`process_started` proves runtime entry, not successful business completion.

Offline regression tests execute a synthetic local stage in a real subprocess,
compare the version/path/interpreter and receipt observed by its command with
the finalized receipt, and test failure without observation and changed-stage
version rejection. No real package download is needed for that evidence.

## Grouped Rollback

Revert the exact-pin policy, root wiring, receipt writer/reader expectations,
regression tests, this migration and release-compatibility generated contract
as one change. Restoring only permissive code while retaining the exact-pin
contract is not a valid rollback. Use an explicitly selected base environment
for recovery; retain stage/activation evidence. Project locks and workspace
bindings must remain byte-for-byte unchanged; a dependency/lock migration
requires a separate explicit decision and must never follow implicitly from a
runtime policy rollback.

## 0.3.15 Operator Scope Migration

This is an unreleased, scoped migration for callers of the public
`OperatorRegistry` and consumers locking its Operator/Model artifacts.
The input and output schemas, not this guide, own exact field definitions.

### Affected Operators

`campaign-outcome-evaluation`, `metric-decomposition`, `scenario-projection`,
`sentiment-aggregation`, and `funnel-diagnosis` retain their exact `@1` identities
and gain explicit `@2` successors. There is no alias or automatic input rewrite.

| Request | Tightened @1 | Explicit @2 |
| --- | --- | --- |
| Omitted mode | Invalid; migration remedy | Invalid input schema |
| Rowwise values or non-additive comparisons | `mode=rowwise`; no cross-row total/share/cumulative | `mode=rowwise` with value scopes; preserves prefix/unknown completeness |
| Additive or permitted semi-additive total | Invalid; aggregation unproven | `mode=aggregate`, complete same-side scopes, allowed axis and evidenced disjoint partition |
| Non-additive total/share | Invalid | Invalid even with partition evidence |
| Linear funnel cumulative | Invalid; lineage unproven | `mode=cumulative`, complete common scope and evidenced root/equal/subset chain |
| Independent or branch-step comparison | Explicit rowwise only | `mode=rowwise`, `topology=independent`; never cumulative |

The four other governed methods (churn profile, payback, elasticity and retention)
keep their existing identities and non-additive support; they do not accept mode.

### Call-Site Changes

For safe legacy comparisons, keep the exact `@1` URI and input schema and add
`mode=rowwise`. Consume only the returned per-row facts. `metrics` no longer
contains totals, shares or cumulative conversion on these legacy methods.

For cross-row output, explicitly select `operator://gravity/<method>@2` and
`gravity.operator-input.governed-method.v2`; consume
`gravity.operator-result.governed-method.v2` including mode and completeness.
Use `gravity operators describe <uri>` to discover the bound schemas, reasons
and limitations. Executable examples live in
[`operator-golden`](../../src/gravity_insight/contracts/operator-golden/).

Aggregation evidence names an axis, the metric's allowed axes, and a disjoint
partition whose members equal the row keys. Both additive and semi-additive
inputs must permit that axis. Non-additive inputs cannot request a total.
Scopes bind each value role to a unit, parent population, inclusive date window
(including timezone and grain), completeness and evidence. Current and reference
windows may differ intentionally; rows summed within either side may not.

Cumulative funnels require a common population, window and unit, unique orders,
and per-row `lineage` evidence. The first row is a root; each later row names the
previous step and declares equal or subset membership. An evidenced subset may
enter fewer users than the previous step reached; equal counts alone are not
membership evidence. Independent scopes can be compared rowwise but not chained.

Evidence references are caller-supplied attestations. Runtime checks their
structure and cross-row consistency offline; it does not fetch source facts or
prove that a declared partition actually is disjoint. Caller Semantic, quality,
privacy and evidence gates remain required. Empty input is rejected; incomplete
input is allowed only rowwise and never relabeled complete.

### Error Handling

Treat `status=invalid`, `ok=false`, `result=null` as a rejection, not a warning or
a usable zero. Follow `error.field` and `error.next_action`:

- `OPERATOR_AGGREGATION_UNPROVEN`: migrate or provide complete partition evidence.
- `OPERATOR_FUNNEL_LINEAGE_UNPROVEN`: provide linear lineage or compare rowwise.
- `OPERATOR_SCOPE_MISMATCH`: align populations/windows before a cross-row claim.
- `OPERATOR_COMPLETENESS_UNSUPPORTED`: complete the input or compare rowwise.
- Existing `OPERATOR_ADDITIVITY_UNSUPPORTED` and `OPERATOR_UNIT_MISMATCH` retain
  their identities and now also guard the scoped methods.

### Models and Handoff

`game-revenue-forecast`, `ltv-curve`, and `segmented-ltv-curve` each have an `@2`
Model and parameter artifact binding `scenario-projection@2`. The retained `@1`
Models still bind `scenario-projection@1` with refreshed rowwise parameter
digests. Relock explicit artifacts outside a running Journey; old digests must
not be silently accepted. LTV ratios use rowwise mode, not totals. These artifacts
validate deterministic mechanics, not project forecast accuracy.

The following eight Skill definitions remain unchanged at their current `@1`
Operator references: payment-conversion-funnel, level-churn-diagnosis,
gift-penetration-optimization, game-campaign-effect-evaluation,
funnel-analysis-misunderstanding-diagnosis, community-weekly-report,
community-daily-report and community-comment-analysis. R2-05/R2-12 own their
content revision, dependency URI/digest, project lock and distribution migration
as one controlled chain. This delivery does not claim that migration is complete.

SDK execution remains owned by `OperatorRegistry.execute`. CLI provides
list/describe/validate, not execution. Plan has no generic governed-method
execution adapter; CoreSkillRuntime/Journey/outcome handoff resolve dependencies,
not these arithmetic methods. No new execution surface is introduced.

### Rollback

Rollback locked artifacts only at a Journey boundary. A safe fallback is explicit
rowwise execution on the tightened `@1`; do not restore pre-fix implicit totals
or cumulative success. Existing `@1` identities are retained for the deferred
Skill migration; their unsafe behavior is removed now, with no removal date for
the safe rowwise identities. Read capabilities are unchanged; supported totals
and linear cumulative analysis remain available through explicit `@2` evidence.
