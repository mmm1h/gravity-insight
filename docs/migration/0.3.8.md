# 迁移到 0.3.8

## Segment 自定义事件规则拒绝

消费方如果把 Segment evaluate 的未知上游拒绝写死为
`INPUT_INVALID / caller / field=input`，需改为识别
`SEGMENT_EVENT_RULE_ACCEPTANCE_UNPROVEN / upstream / retryable=false`。`field` 指向实际被拒绝的
`user_event_rules.groups[N].conditions[N]`，`next_action` 给出关闭缺口所需的同形配对脱敏收据；
不要按这个 code 推断所有自定义事件都失败。

读取 `gravity analysis segment evaluate --spec-schema` 的调用方也需接受
`schema_version=gravity-insight.segment-rule-spec.v2`，以及
`event_support.default_status=requires_live_metadata_and_event_specific_acceptance`，并读取新增的
`metadata_validity_proves_endpoint_acceptance=false` 与 `acceptance_gap`。两个 #15 preset 仍是唯一
本地预检即拒绝的事件；其他事件继续先过元数据校验，只有 endpoint 实际拒绝已观测静态计数形状
时才返回上述 gap code。

首次暴露 cohort 不得回退到普通事件日 Retention；它复用重复参与者且没有 NOT-before 集合。
正/负静态窗口的目标 spec、set-once 属性这一唯一无持久化条件分支，以及当前缺少通用聚合绕行的
原因见[复合 cohort 留存替代路径](../guides/retention-cohort-alternatives.md)。

## SQL Verification 串行与 Evidence v2

`gravity sql verify` 不再并发验证 registered SQL products。调用
`verify_all(..., max_workers=N)` 的 SDK 消费方必须删除该参数或固定传 `1`；直接调用
`build_evidence()` 的维护工具必须显式传入经验证的有序 `verification` history，不再自动伪造
`single_run`。产品读取能力和产品合同没有删减，只改变调度方式。命令遇到最终 429 时返回并保存
不可发布的严格前缀 checkpoint；在同一日期上用 `--resume` 续跑，不能指定产品，也不能跳过失败项。

新生成 Evidence 的整数 `schema_version` 从 1 升为 2，并增加 `verification`：

```json
{
  "verification": {
    "mode": "resumed_after_rate_limit",
    "segment_count": 2,
    "segments": [
      {
        "sequence": 1,
        "started_at": "2026-09-04T10:00:00+08:00",
        "completed_at": "2026-09-04T10:05:00+08:00",
        "products": ["product-a", "product-b"],
        "status": "rate_limited",
        "failure_product": "product-c"
      },
      {
        "sequence": 2,
        "started_at": "2026-09-04T10:05:30+08:00",
        "completed_at": "2026-09-04T10:08:00+08:00",
        "products": ["product-c"],
        "status": "complete",
        "failure_product": null
      }
    ]
  }
}
```

严格反序列化新输出的消费者应接收该字段与 v2。Runtime reader 仍接受现有不可变 v1 Evidence，
因此升级本身不会使已经发布的读取证据失效；下次成功验证会自然发布 v2。

失败输出不再是通用 `ERROR:` 文本，也不直接回显内部 checkpoint。CLI 使用新的
`gravity.sql-verification-result.v1`，其 `failure.sql_code`、`stage`、
`upstream_error.category`、`retryable`、`reached_sql_engine` 和 `execution_evidence` 与
`sql query` 共享分类来源；`failure.code=RATE_LIMITED` 只表示 verify 可续跑，底层 SQL 分类仍在
`failure.sql_code=SQL_HTTP_RATE_LIMITED`。严格前缀的完整结果留在 workspace 私有
`gravity.sql-verification-run.v1` checkpoint，公开 `progress` 只给计数和当前失败产品。

这是新增的 failure-only v1 envelope，不改变 `gravity-sql.query.v1` 或成功 Evidence v2；退出码
仍按 caller/upstream/local 为 2/3/4，最终 429 仍为 3。消费方应按字段判断，不解析 `message`。

## Repository Map v2

0.3.8 将 Repository Map 的整文件 JSON 传输从展开的 v1 表示改为可逆的 v2 表编码。
255,000 字节门槛不变；变化只消除重复编码，不裁剪 entry 字段、issue location、模块节点或边。

## 受影响人群

- 直接读取 `gravity_insight/contracts/generated/repository-map.v1.json`，或假定
  `entries` 是对象数组、`issue_index` 直接映射 location 对象、`module_graph.edges`
  是模块全名邻接字典的消费者，需要迁移。
- 通过仓库内 `scripts.repository_map.load_repository_map`、`scripts/task_context.py`
  或 validation-observability 读取的消费者不受逻辑形状影响；loader 会先校验 v2，
  再还原并校验完整的 `gravity.repository-map.v1` fact document。

## 新旧路径与形状

文件路径从：

```text
src/gravity_insight/contracts/generated/repository-map.v1.json
```

改为：

```text
src/gravity_insight/contracts/generated/repository-map.v2.json
```

v2 仍是一次 `json.load` 可完整读取的普通 JSON，不是 gzip、分片或外部索引：

- `entries` 使用固定 `fields`、排序 `strings` 和 `rows`；row 内负整数 `-N-1`
  指向 `strings[N]`，非负整数仍是原 fact 数值。
- `issue_index.paths` 保存唯一排序路径，`issue_index.issues` 的每个 location 为
  `[path_index, line]`。
- `module_graph.nodes` 保存唯一排序模块名；`module_graph.edges[i]` 是节点
  `nodes[i]` 的 target node index 列表。

仓库内消费方应继续使用 loader：

```python
from scripts.repository_map import load_repository_map

repository_map = load_repository_map()
# repository_map["entries"] remains the expanded object list.
# repository_map["module_graph"]["edges"] remains the full-name adjacency map.
```

原始 JSON 消费方必须按上述三个表解码，并在解码后按
`repository-map-v1.schema.json` 校验；不能把 index 当作业务值。仓库的可执行等价性
断言为：

```powershell
.venv/Scripts/python.exe -m pytest -q tests/test_repository_map.py
```

其中 `test_v2_transport_round_trip_preserves_every_v1_fact` 逐 entry、逐字段比较，
同时比较完整 issue index、节点集、边集和其余顶层事实；越界 table reference 会失败关闭。

## 不迁移的结果

继续读取旧路径会得到文件不存在；直接按 v1 raw shape 读取新路径会把 table 当作旧对象，
从而产生类型错误或错误的图遍历。v2 不提供旧文件副本或隐式 raw-shape alias，因为那会把
已消除的重复重新计入整文件预算。

## 能力保持与回滚

v2 解码结果必须继续通过 v1 fact schema；生成器、checked-in map 和 loader 的往返结果
必须完全相等。因此所有原 entry 字段、issue location、691 个基线节点和 3,718 条基线边
均可恢复，读取能力没有损失。

回滚时同时恢复 v1 生成器、schema/path 与 checked-in v1 文件。不要只恢复旧文件名，
也不要让 v1 generator 与 v2 checkpoint 交叉运行。
