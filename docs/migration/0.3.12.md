# Migrating to 0.3.12

本版把四处"一个信号同时表示两件事"的缺陷拆开，并把跨 operation join key 从字段名猜测
收口为机器契约。四条 Hard break 各自独立，可分别评估。

## 1. `ResponseProjection` 新增字段改变了位置参数顺序

**受影响**：直接按位置构造 `ResponseProjection` 的 SDK 消费方与测试夹具。从合同加载
（`ResponseProjection.from_config`、`load_operation_manifest`）的调用方不受影响。

`dynamic_key_patterns` 插在 `numeric_paths` 与 `empty_object_as_empty_page` 之间，因此
旧的位置调用会把布尔值绑到映射字段上：

```python
# 旧写法：0.3.12 起把 True 绑给 dynamic_key_patterns
ResponseProjection("page", (...), (...), ..., numeric_paths, True, False, ())

# 新写法：用关键字
ResponseProjection(..., numeric_paths=numeric_paths, empty_object_as_empty_page=True)
```

**不迁移的结果**：`TypeError`，或更糟——静默把非映射值当成 `dynamic_key_patterns`。

私有的 `models._response_projection_schema` 同时迁到公开模块
`gravity_insight.response_projection_schema`，函数名 `response_projection_schema()`。旧
私有名不再存在，且原本就不是公开接口，无弃用期。

## 2. Capability validation summary 必须携带 `data_evidence_status`

**受影响**：构造或校验 `capability-validation-summary-v2` 的消费方。

`data_evidence_status` 已进入该 schema 的 `required`，取值为四态之一：

| 值 | 含义 |
|---|---|
| `nonempty` | 投影出了行 |
| `confirmed_empty` | 上游明确回报空（`page.total_items == 0` 或 HTTP 204） |
| `inconclusive` | 无法判定，包括信号互相矛盾 |
| `not_evaluated` | 本次未做该判定 |

**为什么必须改**：投影为空从来不能证明"没有数据"。一个响应如果每个已声明字段都恰好
没命中上游载荷，投影结果与真正的空结果完全一样。0.3.12 之前两者都记成"空"，于是
"没查到"和"查错了"无法区分。现在只有上游的明确信号才给 `confirmed_empty`；同时出现
非空投影数据与明确空信号时 fail-closed 记 `inconclusive`，不再静默二选一。

**不迁移的结果**：0.3.12 之前产出的 summary 无法通过 schema 校验。

`capability-validation-run-v2.schema.json` 里该字段是**可选**的，所以已存储的 run 仍
可读，无需回填。

## 3. `analysis.user_detail.list` 升到 `contract_version: 4`

**受影响**：持有该 operation Validation Result 的工作区。

新增八个已观察顶层字段 `bytedanceMid1_name` … `bytedanceMid8_name`（已观察字段
153 → 161），`contract_fingerprint` 随之改变。

**不迁移的结果**：按版本 3 记录的 Validation Result 会被判
`CAPABILITY_FINGERPRINT_MISMATCH` 并隔离，依赖它的 Journey 报
`DEPENDENCY_VALIDATION_UNKNOWN`。

**迁移做法**：对该 operation 重新采集并写入 Validation Result。这是可解的状态，不是
合同上的死锁。

## 4. `analysis.funnel.query` 指纹变化

**受影响**：同上，仅限该 operation。

它是唯一声明 `response_projection.dynamic_key_patterns` 的 operation。指纹载荷只在该
字段非空时才输出它，因此**其余 236 个 operation 的指纹不变**，不需要重采。

## 5. `analysis.order_detail.list` 的 completeness 升到 `complete`

**受影响**：持有该 operation Validation Result 的工作区；以及此前因它的
`completeness: unknown` 而无法满足依赖的 claim-bearing Capability。

`contract_version` 2 → 3，`pagination.completeness` `unknown` → `complete`，
`pagination_evidence` `template` → `production`。

这是**能力增强**：该 operation 现在可以满足要求完整集合的依赖。但指纹随之改变，
按版本 2 记录的 Validation 会被隔离，需重新采集。

升级依据是三项证据同时成立，2026-09-07 的生产观测：末页回显匹配、SDK `has_more=false`、
累计条数等于 `total_number`。**53 个候选里只有它一个满足**——其余保持 `unknown`，
原因逐条记录在
[脱敏取证收据](../../evidence/forensics/20260907_operation_recertification.json)：
31 个返回空集且 `total_page=0` 与 page 1 不匹配，13 个的总页数超出安全预算
（例如 `analysis.monetization_detail.list` 有 126,854 页），其余是父级查找无可选值或
探测输入不可用。**判据没有放宽。**

## 6. `analysis.scatter.query` 补登记十三个嵌套数值路径

**受影响**：同上，仅限该 operation。

`contract_version` 1 → 2，在 `aggregate_by_date`、`date_list` 和 `y` 下登记了生产响应
本来就在返回的十三个数值路径（`proc_zone`、`stat_total`、`zone_stat_sum`、
`zone_stat_users`、`is_total`、`total_another_event_*`、`total_another_users`、
`total_user_num`）。此前它们不在契约里，因而被投影丢弃。

没有读取能力损失，也没有改变调用参数或结果 envelope；只是指纹变化需要重采。

## 7. Skill 随 wheel 分发并自动装配（Soft break）

**受影响**：所有通过 wheel 安装并使用根 `gravity` CLI 的用户；以及任何断言 wheel 内
不存在 Skill 路径的构建检查。

**这是对 0.3.5 那条已发布 Hard break 的部分回退。** 0.3.5 曾把业务 Skill 的唯一分发
入口收敛到 Skill Hub，明确写着「Runtime wheel 不再携带」。所以本次变化必须显式声明，
不能当成无感改进。

### 回来的是什么，没回来的是什么

| | 0.3.4 及以前 | 0.3.5–0.3.11 | 0.3.12 |
|---|---|---|---|
| wheel 内 Skill 注册表 | 有 | 无 | **仍然没有** |
| wheel 内密封 seed | 无 | 无 | 有，单一归档 |
| 首次装配 | 直接读 wheel | 需显式配置 | 自动，离线 |

回来的只有一个密封归档 `gravity_insight/skill_seed/skill-seed-v1.zip`，93 个资产、
44 个 Runtime Skill 与 44 个 Agent Skill。**没有**回来的是 wheel 拥有的注册表：
`gravity_insight/skills/` 与 `gravity_insight/contracts/skills/` 都不存在，
`scripts/generate_skill_library.py` 仍是唯一构建 Owner，wheel 只是同一产物的密封镜像。

### seed 不是信任捷径

seed **不直接进入发现面**。首次装配仍然走完整链路：source/index 编译 → 精确 managed
lock → 归档校验 → CAS 写入 → 最终 verify，且 `network_called=false`。篡改 seed 会
fail-closed 并保留 last-known-good。

原因是这条链里**没有签名或公钥信任根**：SHA-256 保证的是"相对于已选 source/lock 的
完整性"，不证明"谁有权发布新的 source descriptor"。让 seed 绕过验证等于把调用方显式做
的来源信任选择偷偷拿掉。

### 关闭方式

```bash
GRAVITY_INSIGHT_AUTO_SKILLS=0    # 接受 0/false/no/off
```

**它和 `GRAVITY_INSIGHT_AUTO_UPGRADE` 是两个独立开关**，这是刻意的：用户可能想继续
接收 Runtime 安全更新，同时冻结 Skill 内容。复用同一个布尔会强迫二选一。

### 不装配的路径

`doctor`、`--help`、`--dry-run`、测试与评测路径不自动装配；`import gravity_insight`
无文件写入、无网络副作用。装配失败**不改变无关业务命令的退出码**，但真正依赖缺失或
未验证 Skill 的调用仍然 fail-closed。

### 永不改写项目锁

装配**永不改写**项目目录下的 `gravity.skills.lock.json`。锁定旧版本时只报
`update_available=true`，升级仍须显式 `gravity skills update` 并走项目评审。

用 `gravity skills status` 查看 active source/index/seed digest、Skill 数、最后尝试、
`network_called`、状态与 reason code。该命令区分**「尚未装配」与「合法的 0 个 Skill」**，
不把两者都表现成静默的 `count: 0`。

## 动态 key 形状：为什么不是正则

`dynamic_key_patterns` 把一个已声明的 data 路径映射到**具名**形状，目前只接受
`iso_date` 与 `decimal_19`。**不接受任意正则**——正则会让合同变成一个可以表达任何东西
的逃逸口，届时"声明过"就不再意味着"被约束过"。

`iso_date` 还会拒绝非日历日期（如 `2026-02-30`），且每个声明路径的根必须是已声明的
`data_key`。

效果：`analysis.funnel.query` 可以返回合法的日期分桶聚合分组，而不会让每个新日历日
读成 additive 漂移；同时用户属性分组仍然 fail-closed——日期不能冒充 `$os` 这类请求维度。

漂移声明新增两个 reason code：`declared_dynamic_key`（形状匹配）与
`dynamic_key_shape_mismatch`（已声明但形状不符）。未声明的动态 key 仍报
`dynamic_key_requires_review`，该码未变更、未移除。

## 新增能力（无需迁移）

**漂移归因**：漂移记录新增 `expectation_provenance`，钉住 operation 合同 digest 与
版本、Runtime 版本、request shape 指纹、已接受的上游基线与对应的当次观测。此前漂移
只能报"不一致"，无法区分是上游变了还是本地预期写错了。

**凭据世代标识**：HTTP 收据新增可选 `credential_scope_opaque_id`，公开接口
`gravity_insight.runtime_scope.credential_scope_opaque_id()`。它是持久化在 principal
scope 目录内的随机 64 位十六进制标记（权限 `0600`），**不由凭据推导、也不泄露凭据
材料**，只用于按凭据作用域给收据分组。

**join key 契约**：

```python
from gravity_insight.contracts.join_key import resolve_proven_join_key

mapping = resolve_proven_join_key(platform="bytedance", object_type="material")
```

按 `platform`、`object_type` 和可选 `object_subtype` 解析，返回精确的左右
operation/path 对、规范化规则与观测证据。`namespace_status` 是三态——`proven`、
`disproven`、`insufficient_evidence`——只有未超过 `revalidate_after` 的 `proven` 可解析，
其余一律抛 `JoinKeyContractError`。机器真相位于 `contracts/join-keys/registry.v1.json`，
由 `join-key-registry-v1.schema.json` 校验。

这条替代的是"按字段名猜 join key"。此前 `bytedanceMid1..8` 的业务语义未经证实，跨平台
尤其危险：快手与腾讯的素材 ID 实际落在名字带 `bytedance` 前缀的字段里。契约让这类事实
可查询，而不是靠读者记住。

## 旧写法移除计划

- `ResponseProjection` 的位置构造：无过渡期。它是 frozen dataclass 的字段顺序，无法同时
  保留两种顺序。
- `models._response_projection_schema`：私有名，已直接移除。
- 版本 3 的 `analysis.user_detail.list` Validation：由指纹机制自动隔离，无需手工清理。
