# 外部做法借鉴规划

## 目的与判定口径

这份规划只服务一个目标：**分析师不打开引力 Web，也能在本仓库内发现能力、完成分析、判断结果是否可信，并在失败时知道下一步怎么走。** 外部项目的做法只有能缩短或补全这条动线时才进入排期；协议覆盖率、工具数量、模型新颖度和界面完整度都不是独立目标。

优先级含义如下：

- **P0 现在做**：当前能力缺口或高频硬阻塞，且已有足够证据决定方向。
- **P1 下一批**：能补全或显著缩短动线，但依赖 P0、上游安全证据或逐项合同证据。
- **P2 记着但先不做**：方向可能有价值，当前没有用户阻塞、重复消费者或可靠证据支持立即投入。
- **P3 明确不做**：与目标、仓库边界或风险收益不匹配；除非前提发生变化，不再重复立项。

工作量粗分为 S（约 3—5 个工程日）、M（约 1—2 周）、L（约 2—4 周）和 XL（跨轮次、超过 4 周）。它们是排序量级，不是承诺工期。

## 基线与证据边界

本规划采用任务给定、并可由本机 `codex/write-kanban@cf71ae7` 复算的近期整合态作为产品排序基线：223 个 operation、11 个 manifest，稳定面为 184 个读 operation 加 30 个受治理写 operation；产品动线为 52 条，其中 43 条闭环、1 条部分闭环、8 条完全缺失。当前规划 worktree 固定在 `dev@4646347`，其编译结果仍为 205 个 operation，当前版[产品动线台账](../analysis-journeys.md)仍是 51 = 42 / 1 / 8。因而以下排期以看板写能力先完成常规整合为前提，不把尚未出现在本分支的代码当成当前事实。

另外三条边界会直接影响优先级：

1. 路由的 `260/336` 与干净外部 LLM 的 `325/336` 都是开发集结果，不是受保护 holdout 结论；它足以改变工程方向，但不足以宣称泛化已经证明。证据见[路线图中的臂 C 重跑结论](../roadmap.md)。本规划不读取 holdout/final，也不接触密钥。
2. 8 条完全缺失动线主要卡在安全的非空样本、父对象或响应合同证据；语义编排不能凭空补出这些证据。1 条部分闭环动线仍有 6 类服务端导出缺少成功文件形态。
3. 自定义指标 CRUD、metadata 数据字典与维度表 CRUD、SQL 工作台已经在既定排期中。下面的语义组合层建立在它们之上，不另造平行注册表。

## P0：现在做

### P0-1 目录优先的宿主 LLM 选路

- **来源**：Amplitude 的渐进式发现先暴露类别、类别工具和描述，而不是一次展开全部工具；LangChain 的 structured output 允许 0 到多个选择并显式处理 malformed 结果。分别见 [MCP 调研“渐进式发现”](mcp-protocol-and-servers.md)和[语义路由调研“LangChain 多阶段工具选择”](oss-semantic-and-routing.md)。工具描述应包含“做什么/返回什么、解决什么目标、与相邻能力的边界、前置条件”，见[可用性调研的工具描述方法](agent-usability-methods.md)。
- **我们现在是什么样**：仓库已有 canonical Agent card、产品/operation/gap 三层目录和确定性参数校验，但默认 recognizer 仍把大量自然语言先压到自写规则。开发集上 recognizer 为 `260/336`，给干净外部 LLM 完整能力目录为 `325/336`；后者 11 个失败中 9 个是产品选错、2 个是候选集机制问题。说明主要瓶颈已不是继续扩关键词，而是目录边界和宿主选择合同。该结论尚未经过受保护集。
- **借鉴什么**：把版本化、紧凑的产品目录作为宿主模型的首选发现面；宿主只返回 0 到 N 个候选产品及结构化理由，随后仍由本仓库执行 `describe`、参数解析、合同校验和 Plan 编译。找不到能力必须返回 canonical gap，不能让模型改写 operation 或绕过治理。停止以扩大 recognizer 关键词表作为主路线；recognizer 保留为无模型离线回退。目录继续从现有 owner/card/gap 投影，不新建第二套 registry，也不在仓库内绑定单一模型厂商。
- **为什么值得**：这是“已经能做但经常走错入口”。不做时，分析师用自然语言询问一个已闭环能力，会在第一步被分到错误产品；开发集已有 76/336 个此类 recognizer 失败，之后参数再正确也无法执行。做完后，分析师可以先得到正确产品或明确 gap，把时间花在分析而不是猜 CLI 子命令。
- **代价**：M。主要修改 canonical 目录投影、宿主选择 JSON 合同、候选校验、评测与 CLI/Plan 入口；不会增加上游 HTTP 请求。不可逆影响是默认发现路径改变，因此必须保留确定性离线回退，并用一次性受保护评测作为切换门槛。
- **优先级**：**P0**。
- **能力还是顺手**：顺手性问题，不新增上游读能力；但它位于所有自然语言动线的第一步，阻塞面大。
- **不做会卡在哪一步**：`自然语言问题 → 选择产品`；选择错后会得到无关参数错误、错误 gap，或根本无法生成 Plan。
- **可证伪验收**：开发集至少保持 `325/336`，0 个候选、多个候选和 malformed 输出都能确定性处理；写产品的选择不得触发写入。由受保护集保管者按预先冻结的成对方案运行一次，只有相对 recognizer 提升至少 10 个百分点、且安全用例零回归时才切默认路径；达不到就只交付目录合同，不切默认。

### P0-2 用上游账号 owner 替代 SDK marker 作为归属事实

- **来源**：Snowflake、Cube 和 Looker 的共同做法是复用上游身份、角色、行列策略和审计，而不是在 agent 层另造权限事实；远程或多人场景还要区分调用者、被代表用户和上游凭据。见[安全治理调研 E03、I11—I13](agent-security-governance.md)。
- **我们现在是什么样**：30 个受治理写 operation 覆盖分群、报表、报表订阅、看板 space/folder/dashboard/note。更新和删除以 SDK 写入的 `GSDK-...` marker 证明“这是本 SDK 创建的对象”；marker 缺失即 `OWNERSHIP_MARKER_REQUIRED`。这能防止误删未知对象，但 marker 不是账号 owner，也不能证明当前调用者有权操作对象。因此分析师无法用仓库治理账号内由自己或既有流程创建的对象。
- **借鉴什么**：逐对象族研究并投影上游 owner/creator/tenant/role 事实，读回时将其纳入版本化归属判据和审计收据；marker 降级为来源/兼容证据，不再充当唯一权限事实。更新和删除仍保持 describe/dry-run/显式确认，foreign、shared、owner 不可判定时一律拒绝。先从具有稳定 owner 字段和安全测试对象的对象族开始，不能用名称、备注或列表可见性猜 owner。
- **为什么值得**：这是“现在做不到”。不做时，分析师能读取一个账号内已有分群或报表，却会在“修改/清理这个我拥有的对象”处被 marker 拦住，只能回 Web。做完后，仓库可以治理账号中当前用户确实拥有的既有对象，同时继续拒绝他人或归属不明对象。
- **代价**：L—XL。需要逐对象族补充安全合同证据、身份绑定、Plan/SDK/CLI 归属展示、审计和破坏性路径测试。不可逆影响是扩大可更新/删除对象集合，风险高；必须按对象族独立放行，不能一次全开。若上游没有稳定 owner 事实，该对象族保持 marker-only，而不是猜测。
- **优先级**：**P0**。
- **能力还是顺手**：能力缺口；现有写能力只能完整治理 SDK 自建对象。
- **不做会卡在哪一步**：`列出既有对象 → 选择自己拥有的对象 → dry-run update/delete`；在归属判定处失败并被迫回 Web。
- **可证伪验收**：对每个放行对象族，用安全测试账号覆盖三类对象：同账号 owner 且无 marker 的对象可完成 dry-run 和经确认的更新/删除；foreign/shared 对象被拒绝；owner 字段缺失或漂移时在网络写调用前失败。审计记录必须同时给出 caller、upstream owner、判定依据和 HTTP receipt。任何一类不能可靠区分，该对象族不验收。

### P0-3 受治理的语义组合层与可机读来源链

- **来源**：dbt Semantic Layer、Looker/LookML 和 Snowflake Cortex Analyst 都把指标、维度、时间粒度、连接和访问策略放在受治理语义对象中；MetricFlow 的 saved query 保存结构化查询，而不是只保存一句原话。详见[语义层与 Text-to-SQL 调研“Tier B”建议](semantic-layer-and-text2sql.md)和[开源语义路由调研的语义层比较](oss-semantic-and-routing.md)。厂商同时强调“how it was computed”，见[厂商 landscape 的共性结论](vendor-agent-landscape.md)。
- **我们现在是什么样**：窄切片已经扩到同 ID 的四个不可变版本。`@1` 保留最初一个指标与空 filter，`@2` 增加 dimension-bound `click_company IN` 和 3 个 day/week 指标，`@3` 以粒度与代表性维度实证登记共 13 个成员，`@4` 保持成员面并把结果收窄为 fetched-at 时点观察，同输入跨执行不保证数值相同。结果继续带定义版本、实际成员、生成查询、验证和 `allowed_claims`。它仍不是跨产品通用层：只有一个 dimension/filter/join profile，v3/v4 的 5 个成员维度兼容性明确是同族外推而非逐成员实测，verified query 仍以精确问句绑定语义上下文。
- **借鉴什么**：沿现有窄 Tier B 编译器逐个增加有生产证据的版本化定义。输入只能引用已注册且版本化的指标、维度、过滤器、时间粒度和允许连接；编译前验证粒度、连接基数和访问范围，不能识别的成员或 join 在发网前失败。结果扩展现有来源链，记录 `resolution_tier`、定义 ID/版本、实际语义成员、生成查询（若有）、验证结果和允许声称的结论。继续复用 composite / plan adapter / agent card，不建设通用语义平台。
- **为什么值得**：这是“现在做不到”。不做时，分析师提出“同一个已登记指标，换一个已登记维度、过滤条件或时间粒度”但没有现成产品时，会在能力映射处得到 gap，或转去 Web/手写 SQL；即使 SQL 跑通也无法从结果判断口径是否一致。做完后，已治理成员之间的新组合可以直接在仓库完成，并且结论可追到定义版本。
- **代价**：XL。涉及语义合同、编译器、来源链、Plan/SDK/CLI、质量门和少量端到端测试，并依赖三项既定排期。不可逆影响是语义定义会成为结果解释的一部分，所以定义版本必须持久化，旧结果不能被新定义静默重解释。
- **优先级**：**P0**。原“三项依赖全部完成”的顺序前提已被事实改写：自定义指标 CRUD 已闭合；维度表由产品方搁置；SQL 工作台 route 在 Census 中不存在。首个窄切片因此不再等待这三个条件，但任何新成员仍须自己的合同与生产证据。
- **能力还是顺手**：能力缺口；它补的是预定义产品之外、但仍由已登记语义成员组成的问题。
- **不做会卡在哪一步**：`识别业务问题 → 找到已有指标和维度 → 组合查询`；没有精确产品时只能返回 gap、手写 SQL 或回 Web。
- **可证伪验收**：至少选 3 个此前没有专用产品、但仅使用已登记成员的真实组合，均能从同一结构化输入确定性编译并返回结果；未知成员、禁止 join、粒度冲突在 0 次上游请求下失败；每个结果都能由定义 ID/版本和实际成员重放。人工复核若发现任一结果在 SQL 成功时仍给出超出 `allowed_claims` 的结论，则不验收。

## P1：下一批

### P1-1 一次引导式冷启动

- **来源**：Amplitude 用 4 个初始发现工具渐进展开能力，Benn Stancil Labs 也采用极小入口面；这说明“少量稳定入口 + 按需展开”比要求用户背完整工具树更适合作为 agent 冷启动。见 [MCP 调研的工具组织比较](mcp-protocol-and-servers.md)。
- **我们现在是什么样**：现有十分钟路径在空缓存下需要 12 条命令、7 次 HTTP，才能完成第一条真实事件分析。步骤是确定且有界的，但分析师需要理解项目、App、事件、字段、值和 Plan 的先后关系。
- **借鉴什么**：增加一个引导式 bootstrap/plan 入口，收集最少的项目、时间范围和目标，复用现有 metadata sync、describe、Plan 和有界 worker pool，自动推进到“可执行 Plan”或返回唯一下一动作。它不能隐藏默认项目、扩大 HTTP 总量或绕过缓存/合同。
- **为什么值得**：这是“能做但不够顺手”。不做时，新用户会在项目/App/事件/字段的依赖顺序中反复切命令；做完后，首次真实查询只需表达目标并确认 Plan。
- **代价**：M。主要动 CLI/Plan 编排、进度事件和 ten-minute 文档；复用现有读操作，无不可逆上游影响。
- **优先级**：**P1**，排在 P0-1 的目录合同之后。
- **能力还是顺手**：顺手性。
- **不做会卡在哪一步**：`空缓存 → 找项目/App → 找事件/字段/值 → 生成第一条 Plan`，任一前置项漏掉都会变成下一条人工排障命令。
- **可证伪验收**：从空隔离缓存和有效凭据开始，在不超过 2 次顶层调用、总计不超过 7 次 HTTP 的条件下得到可审阅 Plan 并执行首条事件分析；任何缺少前置证据的情况必须给出一个确定下一动作，不能静默选默认项目。

### P1-2 可恢复的分析 playbook

- **来源**：ThinkingAI 把 Skills 表达成目标、方法、步骤和可重放流程；火山引擎深度分析公开的是“问题—假设—验证—结论”并允许步骤干预和重算。见[厂商 landscape 的 ThinkingAI 与火山引擎章节](vendor-agent-landscape.md)。这里借的是工作方法，不借它们未公开的运行时。
- **我们现在是什么样**：仓库已有单产品 card、Plan、composite 和 handoff，能够执行单次查询；但“指标下降归因”一类多步分析仍需调用者自己串时间对比、分群、漏斗/留存、维度下钻和证据汇总。中途改一个假设时，没有标准的下游失效/续跑语义。
- **借鉴什么**：只为高频闭环分析建立少量版本化 playbook：目标、必要输入、步骤 DAG、每步产品/合同、停止条件、证据引用和允许结论。第一条应选择已有产品可完整支持的“指标异常定位”，支持人工替换假设后仅重跑受影响下游。playbook 编译成现有 Plan/composite，不建 Skill 市场和通用工作流引擎。
- **为什么值得**：这是“各步能做，但完整结论不够顺手”。不做时，分析师会在每个查询之间手工搬运时间窗、过滤器和中间结论，容易丢失证据链；做完后，一条完整调查可以暂停、审阅、修正和重放。
- **代价**：L。涉及 playbook 合同、Plan DAG、局部失效、结果汇总和 1 条端到端样例；无上游不可逆影响。
- **优先级**：**P1**。
- **能力还是顺手**：主要是顺手性，也让“完整分析旅程”变成可验证产品，而不是操作集合。
- **不做会卡在哪一步**：`得到异常 → 提出假设 → 运行多个产品 → 汇总证据`；用户必须在仓库外维护步骤状态和结论来源。
- **可证伪验收**：固定样例能输出问题、假设、每步事实路径和结论；替换一个中间假设后，仅其下游步骤失效并可续跑；故意让一步返回 partial/gap 时，playbook 不得伪造最终结论。

**2026-08-17 首条交付：**`metric-anomaly-localization@1` 已以一个固定 definition、CLI/SDK 和现有
Plan/`semantic_compose` 节点落地；checkpoint 按 DAG 只失效假设后继。生产样例的返回 click-company
行之和为 `2713799.09 → 2123932.39`（`-21.74%`），每步携带 `result_audit` 与结果内 fact path；
bytedance→tencent 后只重跑两个 validate，二者 empty 时结论/claims 为空。partial 与 capability-gap
故障注入同样 fail closed。无维度 v2 total 的生产 `INPUT_INVALID` 证明该既有产品面不够，v1 因而只称
“返回维度行之和”，不伪称完整 App total。它不解锁新问题，故作为既有语义组合的调查编排审计行，
不增加产品动线、operation、产品卡或 selector；完整请求账本见[路线图](../roadmap.md#指标异常定位-playbook-v12026-08-17提案)。

### P1-3 动线级可行动错误

- **来源**：Structured Feedback 的核心不是更长的报错，而是给出失败路径、观察值、允许替代项或明确发现动作；可用性调研建议把错误恢复和 fault injection 纳入分析旅程评分。见[可用性调研“错误恢复与故障注入”](agent-usability-methods.md)。
- **我们现在是什么样**：仓库已有结构化错误、gap、字段建议和多轮 actionable-error 审计，但仍存在只描述错误类型、没有合法值或下一发现操作的 B/C 类错误。单元测试能证明分支失败，不能证明调用者能在预算内恢复完整旅程。
- **借鉴什么**：只针对 P0/P1 触达的用户可见边界，把错误统一补到“路径 + 观察值 + 允许值/发现动作 + 是否可重试”；为冷启动、选路、语义组合、导出各加入一条 fault-injected recovery journey。错误内容继续受隐私与投影规则约束，不能为了可行动泄露未授权候选。
- **为什么值得**：这是“能做但失败后不够顺手”。不做时，分析师会在无效 event、字段、枚举值或 cursor 处停住，只能翻文档或回 Web 找合法值；做完后 agent 能机器决定下一次安全调用。
- **代价**：M—L，按活跃动线分批处理错误投影、CLI/Plan 展示和恢复评测；不要求清零所有历史分支，无不可逆影响。
- **优先级**：**P1**。
- **能力还是顺手**：顺手性和可恢复性。
- **不做会卡在哪一步**：任何 `参数校验/上游 partial → 修正输入 → 继续原旅程` 的第二步；当前有些错误只告诉用户“错了”，没有告诉下一调用。
- **可证伪验收**：P0/P1 活跃边界的 caller-actionable 错误 100% 含路径、观察值和合法替代/发现动作；每条故障注入样例都能由机器在既定调用预算内恢复，不能恢复的必须稳定落到 canonical gap。

### P1-4 不可信结果与写效果隔离

- **来源**：Invariant/AgentDojo 类案例证明工具返回值中的业务文本可以成为 prompt injection；安全调研要求默认最小工具集、把工具结果视为不可信，并将任务成功与安全成功分开评测。见[安全治理调研 E01、I12](agent-security-governance.md)和[开源评测调研的安全第五层](oss-eval-and-drift.md)。
- **我们现在是什么样**：写操作已有 dry-run、显式确认和归属门，LLM 输出也要求 strict JSON 和 origin metadata；但仓库明确不检测 prompt injection，也没有一条端到端评测证明读到恶意事件名、报表标题或备注时，宿主不会因此选择写工具或改变导出目的地。
- **借鉴什么**：在宿主选路/Plan 边界区分数据、指令和授权：工具结果只能提供数据，不能新增写权限、确认写入或修改外部目的地；读到的字符串不得进入工具名/operation/路径控制位。建立“任务成功 + 安全成功”双判据和一组 read→write 对抗样例。不要承诺通用 prompt-injection 检测，只验证本仓库能控制的效果边界。
- **为什么值得**：这是“当前安全动线无法证明”。不做时，P0-1 接入宿主 LLM 后，分析师可能在读取恶意业务字符串后被诱导生成写/导出 Plan；即使最终归属门拦住，目的地或无害写也可能偏离用户意图。做完后，只有用户侧显式输入能授权效果。
- **代价**：M。涉及宿主选择合同、Plan taint/origin 校验、安全评测和少量错误分类；不改变上游合同。不可逆影响很小，但可能拒绝过去被容忍的“从结果文本直接生成写动作”。
- **优先级**：**P1**；P0-1 可以先交付只读目录选择，任何自动衔接写产品都要等本项验收。
- **能力还是顺手**：安全可用性；不增加业务能力，但决定自然语言入口能否安全覆盖写面。
- **不做会卡在哪一步**：`读取业务文本 → 宿主规划下一步 → 进入写/导出产品`；无法证明下一步仍来自用户意图，只能禁用这段自动衔接。
- **可证伪验收**：在事件名、属性值、报表标题、备注和返回错误中注入诱导文本，宿主仍可完成原读任务，但 0 次未授权 mutation，operation、对象 ID 和输出目的地均不被污染；安全失败与任务失败分别计数。

**2026-08-17 完成：**采用模型外 `gravity.host-source.v1` 来源表和规范化 Plan 请求能力，而不是给
字符串打可由模型复写的 taint 标签。tool result 只能是 data；Plan kind/selector/product/name/action 与
tool/operation/path 只能引用 SDK contract；对象 ID/目的地只能引用 user source；mutation preview 绑定
用户对完整请求 SHA-256 的 permission，execute 再绑定同请求的 preview fingerprint confirmation。
第五层二元阈值未改，只加入 7 个本地 read→write safety case，并分别得到任务成功 **7/7**、安全成功
**7/7**、未授权 mutation **0**。关闭隔离的错误消息对照仍完成读任务，但发生 **1** 次 mutation，且
operation/object/destination 均被污染，证明用例有区分力。该结论只覆盖 `execute_host_plan` 边界；外部
宿主绕过它调用 raw CLI/SDK/其他工具的行为仍不可见，不宣称通用 prompt-injection 防护。

### P1-5 补齐 6 类服务端导出

- **来源**：Mixpanel Headless 把查询和导出做成可重放的 typed CLI/Python 工作流；MCP 的长任务/进度模型和 dbt `truncated` 标志都强调异步或截断状态必须显式，不应假装已拿到完整结果。见[厂商 landscape 的 Mixpanel Headless](vendor-agent-landscape.md)和 [MCP 调研的任务、分页与截断](mcp-protocol-and-servers.md)。
- **我们现在是什么样**：`user_event`、`segment.result`、`segment_user_detail`、`user_detail`、`pay_event` 已各用自己的成功文件形态闭环；`origin_event` 仍缺正数 evaluate。`monetization_detail` 的 READY 文件已通过 route-scoped archive policy，但 1,000,000 文件行小于同 scope 的 1,212,315 明细总数且无截断信号，聚合动线因此保持部分闭环。`stream_event` 已判定不适用。
- **借鉴什么**：在获得安全证据后，逐导出族复用统一 task 状态、进度、分页/截断、下载校验和 receipt；每族保持独立合同，不能用一个成功文件猜另一个。所有状态必须区分 empty、partial、truncated、gap、expired 和 complete。
- **为什么值得**：这是“现在做不到”。不做时，分析师完成查询后会在拿完整文件这一步回 Web 或写临时脚本；做完后，适用的服务端导出能在同一 SDK/CLI/Plan 动线闭环。
- **代价**：L，且受每族成功文件证据约束；涉及导出合同、轮询/下载适配器、receipt、隐私复核和每族一个边界测试。没有证据的族保持 gap，不可用猜测推进。
- **优先级**：**P1**。
- **能力还是顺手**：能力缺口。
- **不做会卡在哪一步**：`提交服务端导出 → 判断完成 → 下载并验证文件`；目前只有一个变体能完成全链路。
- **可证伪验收**：6 个适用变体各自有经过隐私审查的成功合同，能从提交轮询到下载并验证非空/空文件；故意制造 expired、partial、truncated 时状态不得被误报为 complete。任何拿不到安全样本的变体继续记为 gap，不算完成。

**2026-08-17 进展：**历史“缺非空样本”理由已对六族重判。现有分群和单日明细足以直接解锁
`segment.result`、`segment_user_detail`、`user_detail`、`pay_event` 四族，均已用自己的非空
XLSX shape 晋升。`origin_event` 仍缺正数 evaluate 样本；`monetization_detail` 不是缺父数据，
而是 READY 文件未通过未放宽的 archive-safety 门禁。聚合动线仍为部分闭环，P1-5 也仍未全部完成；
后续只围绕这两个精确证据条件，不再以“其余六族均缺非空样本”排期。

## P2：记着但先不做

### P2-1 由规范目录生成本地 stdio MCP

- **来源**：MCP 将 tools、resources、prompts 分开；Amplitude、dbt、Snowflake 等把业务结果、目录资源和专家 SQL 逃生舱分层，见 [MCP 协议与服务器调研](mcp-protocol-and-servers.md)。
- **我们现在是什么样**：CLI、SDK、Plan 和 Agent card 已能 headless 使用，canonical 目录也不再需要第二份手工注册表；尚无两个独立消费者证明 MCP 是当前阻塞。
- **借鉴什么**：当至少两个真实消费者明确需要 MCP 时，由 canonical catalog 生成本地 stdio server：结果型产品做 tools，稳定目录/合同做 resources，少量分析模板做 prompts；保留 SQL 为隔离的专家入口。不得 1:1 暴露所有 operation。
- **为什么值得**：可降低标准客户端接入成本，但当前没有分析师因缺 MCP 而无法完成仓库动线。
- **代价**：M—L，涉及协议映射、分页、错误、生命周期和一致性测试；本地 stdio 无不可逆远程身份影响。
- **优先级**：**P2**；以重复消费者和可量化接入成本为升 P1 条件。

### P2-2 把逐字问句绑定升级为结构化保存查询

- **来源**：MetricFlow saved query 保存 metrics、group_by、where、order/limit 等结构，而不是把一句自然语言当稳定键；见[开源语义路由调研的 saved query 比较](oss-semantic-and-routing.md)。
- **我们现在是什么样**：workspace semantic context 支持 verified query，但精确问句匹配会把措辞差异当成语义差异。这是安全但脆弱的做法；目前没有证据表明它是高频阻塞。
- **借鉴什么**：在 P0-3 的版本化语义成员存在后，让 verified question 指向结构化 saved-query ID；问句只作为别名/样例，真正的稳定键是成员、过滤器和粒度。
- **为什么值得**：减少“同义改写未命中”的维护成本，并避免错误复制 exact sentence；不会新增分析能力。
- **代价**：M，需要一次直接 breaking migration 和调用方同步；定义 ID 会成为持久接口。
- **优先级**：**P2**，依赖 P0-3，且先收集实际 miss 证据。

### P2-3 引力原生 AI 只保留为影子评测臂

- **来源**：引力原生 AI 的公开证据仅表明它把自然语言转成事件分析配置 `backup_measure_json`，覆盖窄、没有成功样本、版本合同和结果返回；见[引力原生 AI 调研结论](gravity-native-ai.md)。
- **我们现在是什么样**：仓库已经能生成受治理 Plan 并直接返回结果，覆盖面也远大于事件分析；原生 AI 不能替代结果、来源链和错误治理。
- **借鉴什么**：只有未来拿到合法的成功配置合同、错误分类和可重放样本时，才把它作为事件分析参数生成的第四个离线/影子评测臂，与目录 LLM、recognizer 和确定性校验比较；不进入默认执行链。
- **为什么值得**：它可能减少少数复杂事件参数的构造，但当前证据不能证明，且不是完整分析捷径。
- **代价**：S—M 的评测适配，另有未知的安全取证成本；若必须依赖 Web 会话或不可版本化内部接口则直接放弃。
- **优先级**：**P2**，升档条件是可安全取得成功合同且相对 P0-1 有稳定增益。

## P3：明确不做

以下 9 项在当前产品目标和仓库边界下明确不做。

### P3-1 把 223 个 operation 逐个暴露成 agent tool

- **来源**：PostHog 等服务器公开数百工具，MCP 调研记录了从极少到 844 个工具的巨大差异，见 [MCP 工具组织比较](mcp-protocol-and-servers.md)。
- **我们现在是什么样**：operation 是受治理的上游原子合同，产品 card 才是分析师入口；三层目录已经把执行细节和 gap 分开。
- **借鉴什么**：**不借鉴 1:1 暴露**。只保留少量结果型产品和按需 operation 发现。
- **为什么不值得**：分析师不会因此多完成一条动线，反而要理解分页、内部 ID 和相邻原子操作，选错面扩大。
- **代价**：若做为 L—XL，长期还要同步 223+ 描述和权限；会形成难以收回的公共协议面。
- **优先级**：**P3 明确不做**。

### P3-2 把不受治理的 Text-to-SQL 作为可信默认入口

- **来源**：语义层调研明确指出 execution success 不等于 semantic correctness，原始 Text-to-SQL 应隔离为 Tier C，见[语义层与 Text-to-SQL 调研](semantic-layer-and-text2sql.md)。
- **我们现在是什么样**：结果来源会区分 governed product、caller-defined SQL 和 raw operation；SQL 工作台已在排期，但不把 SQL 成功包装成业务口径正确。
- **借鉴什么**：**不借鉴“模型写出能跑 SQL 就给可信答案”**。SQL 只作为专家探索，必须标记 caller responsibility。
- **为什么不值得**：它会让分析师少看到错误，却不会少得到错误；静默口径、连接和粒度错误直接破坏“完整分析”的可信部分。
- **代价**：表面 S、实际需要无限语义治理；一旦结果被当成可信事实，影响难以逆转。
- **优先级**：**P3 明确不做**。

### P3-3 现在建设远程多人 MCP 与 OAuth 平台

- **来源**：MCP 和安全调研都要求远程场景有 per-request caller、represented user、token separation 和上游身份绑定，见[安全治理 I13](agent-security-governance.md)和 [MCP 传输/认证章节](mcp-protocol-and-servers.md)。
- **我们现在是什么样**：仓库是本地 SDK/CLI/Plan，连上游 owner 事实尚未补齐，也没有远程多租户消费者需求。
- **借鉴什么**：**现在不借鉴远程托管面**；若未来需求出现，另立产品和威胁模型，不能从 stdio 直接加一个 HTTP wrapper。
- **为什么不值得**：它不补任何分析动线，却先引入身份代理、凭据托管、租户隔离和审计平台工作。
- **代价**：XL，安全和运维面不可逆扩张。
- **优先级**：**P3 明确不做**。

### P3-4 建 Skill 市场或追求 100+ Skills

- **来源**：ThinkingAI 宣传大量 Skills，厂商调研同时指出其运行时合同、失败语义和可复现性并未公开，见[厂商 landscape](vendor-agent-landscape.md)。
- **我们现在是什么样**：仓库按可验证产品动线交付，且已有 composite / plan adapter / agent card 三件套。
- **借鉴什么**：只借 P1-2 的结构化方法，**不建设 marketplace、插件机制或按数量考核 Skills**。
- **为什么不值得**：数量不能证明旅程闭环，还会复制 capability registry 并增加陈旧方法。
- **代价**：XL 持续维护，形成新扩展面和治理负担。
- **优先级**：**P3 明确不做**。

### P3-5 建多 agent/A2A 自治协调器

- **来源**：PostHog 曾尝试 coordinator + specialized agents，公开复盘提到 context loss、black box 和维护成本，随后转向 MCP + skills + sandbox；见[厂商 landscape 的 PostHog 章节](vendor-agent-landscape.md)。
- **我们现在是什么样**：当前缺口在合同证据、语义组合和归属，不在并行 agent 数量；现有 bounded worker pool 已处理独立读并发。
- **借鉴什么**：**不借鉴自治多 agent 编排**。P1 playbook 用确定性步骤 DAG 即可。
- **为什么不值得**：它不能补出缺失 schema 或 owner 事实，却让错误来源、调用预算和结论责任更难追踪。
- **代价**：XL，运行与调试复杂度长期不可逆。
- **优先级**：**P3 明确不做**。

### P3-6 把引力原生 AI 当成默认执行捷径

- **来源**：原生 AI 调研未找到成功响应样本、稳定 schema、错误分类或直接结果，只看到事件分析配置和 Web handoff，见[引力原生 AI 调研](gravity-native-ai.md)。
- **我们现在是什么样**：仓库已有版本化 Plan、结果、empty/partial/gap、调用边界和来源链。
- **借鉴什么**：**不把原生 AI 放进生产默认链，也不依赖 Web handoff**；最多保留 P2-3 的条件式影子评测。
- **为什么不值得**：它会重新引入必须打开 Web 的依赖，覆盖更窄，并丢失当前已有的可验证合同。
- **代价**：接口取证和漂移维护成本未知，且依赖非公开内部面，风险不可控。
- **优先级**：**P3 明确不做**。

### P3-7 在 SDK 内复制字段级 ACL、脱敏和 DLP

- **来源**：Snowflake/Cube/Looker 复用上游行列策略；安全调研指出 agent 层不复制字段级 ACL 很常见，见[安全治理 I11](agent-security-governance.md)。
- **我们现在是什么样**：仓库通过固定投影、隐私审查和上游授权控制可见数据，不拥有业务组织的字段权限真相。
- **借鉴什么**：借上游身份绑定和审计，**不在本仓库另建业务 ACL/PII 分类平台**。
- **为什么不值得**：双份权限事实会漂移，既不能可靠多做分析，也可能错误放行或错误遮蔽。
- **代价**：XL、需要持续组织治理，超出 SDK scope 且难以撤销。
- **优先级**：**P3 明确不做**。

### P3-8 从读结果自动执行策略、投放或无确认写入

- **来源**：厂商 agent 有 action/闭环执行趋势，但安全调研要求最小工具面、明确身份和效果审计；见[厂商 landscape](vendor-agent-landscape.md)与[安全治理调研](agent-security-governance.md)。
- **我们现在是什么样**：受治理写仅覆盖仓库拥有的分析对象，默认自然语言 auto-write 为 false，并要求 dry-run 和确认；campaign strategy 不属于仓库。
- **借鉴什么**：**不借鉴自主投放/策略执行，也不取消确认门**。
- **为什么不值得**：这不会让数据分析本身更完整，却把错误结论直接变成业务损失，并越过仓库产品边界。
- **代价**：XL 和高不可逆业务风险。
- **优先级**：**P3 明确不做**。

### P3-9 用固定工具数量或单一 UX 分数作为路线目标

- **来源**：MCP 调研显示公开服务器工具数跨度极大；可用性调研也指出单一综合分会掩盖任务成功、安全、成本和恢复差异，见[MCP 调研](mcp-protocol-and-servers.md)和[可用性评测方法](agent-usability-methods.md)。
- **我们现在是什么样**：仓库按闭环旅程、pass^k、安全层、调用预算和具体失败原因评估。
- **借鉴什么**：**不采用“控制在 5—15 个工具”或一个 UX 总分的硬 KPI**；工具面由产品边界决定，评测保持多维。
- **为什么不值得**：它能优化数字但不保证分析师多完成一件事，还可能诱导拆并工具来刷指标。
- **代价**：实施成本小，错误激励的长期成本大。
- **优先级**：**P3 明确不做**。

## 建议实施顺序与依赖

1. **基线闸门**：先整合并复算看板写能力，使 `223 / 11 manifest / 52 = 43+1+8` 成为当前分支事实；若整合结果不同，重新检查本文所有数量，不静默沿用。
2. **第一条并行证据线**：P0-1 冻结目录选择合同并做开发集重放；P0-2 分对象族调查稳定 owner 事实。两者都不需要增加生产请求量，真正的 owner 合同放行仍按 probing 规范另行批准。
3. **第一条产品线**：在既定自定义指标、metadata CRUD、SQL 工作台的最小稳定面后，实现 P0-3 的一个窄 vertical slice；先证明 3 个组合，不追求通用语义层。
4. **串行整合 shared spine**：所有会触及 `plan_adapters.py`、`agent_capabilities.py`、`agent_composite.py` 和 `agent_handoff.py` 的最终 wiring 由单一 integrator 串行完成；目录、对象族证据和语义核心可独立开发。
5. **下一批闭环**：P1-1 和 P1-3共同缩短并修复冷启动，P1-4 是宿主选路进入写面的前置安全门；P1-2 在 P0-3 可组合后落第一条调查 playbook；P1-5 按取得安全样本的导出族逐个交付。
6. **P2 升档门**：MCP 需两个真实消费者；structured saved query 需 verified-question miss 数据且 P0-3 已稳定；原生 AI 需安全成功合同和可复现实测。没有门槛证据就不投入。

## 已过时、已被后续实测改写的调研结论

调研的外部事实仍有价值，但以下“对本仓库现状/方向”的结论不能再原样用于决策：

- [agent-usability-methods.md](agent-usability-methods.md) 当时基于较小的 8/20、4/20 和 193/240 证据，只能建议比较宿主 LLM、hybrid 与 recognizer。后续同一 336 条开发集已给出 `260/336` 对干净目录 LLM `325/336`，所以“是否值得走目录 LLM 尚不明确”已被改写为“目录清晰度是主路线，recognizer 是离线回退”。受保护泛化仍未证明。
- [oss-semantic-and-routing.md](oss-semantic-and-routing.md) 建议继续做三臂/embedding selector，并引用 Semantic Router 在同一数据上拟合评估的提升。后续干净外部 LLM 实测已经推翻“需要先押 embedding hybrid 才能提高选路”的工程方向；其关于 abstain、结构化 saved query 和语义层的结论仍有效。
- [mcp-protocol-and-servers.md](mcp-protocol-and-servers.md) 的仓库基线是约 185 operation、47 条旅程、20—21 张 card，并认为尚无可运行的工具选择评测。现在已有 223/52 的近期整合态、canonical catalog parity 和 336 条目录选择实测；协议分析仍有效，但“先用 MCP 实验才能知道目录是否可选”已经过时。
- [semantic-layer-and-text2sql.md](semantic-layer-and-text2sql.md) 使用 47 = 32/0/15 的旧动线基线。当前为 52 = 43/1/8，预定义产品覆盖显著提高；“仍缺受治理组合层”没有过时。
- [oss-eval-and-drift.md](oss-eval-and-drift.md) 建议增加 safety 第五层、pass^4 和方向性漂移。前两项及响应侧 additive-only 漂移记录已经落地，所以它们不再是新借鉴项；其 fault injection、oracle health 和任务/安全分评仍有效。
- [agent-security-governance.md](agent-security-governance.md) 中“未知响应字段一律 fail-closed”的现状描述已被方向性漂移策略取代：响应新增字段可在投影外记录 drift 并继续，缺失/类型变化等破坏性漂移仍失败。其上游身份、最小权限和不可信输出结论仍有效。

[gravity-native-ai.md](gravity-native-ai.md)、[segment-delete-capability.md](segment-delete-capability.md) 的核心判断没有被后续证据推翻；前者仍缺成功合同，后者关于“不能只按 path/method 做能力 census”的教训仍适用。[vendor-agent-landscape.md](vendor-agent-landscape.md) 的厂商数量和版本会随时间变化，但本规划没有把这些时效性数字当排序依据。

## 已经借到、无需重复建设的做法

- **仓库已经做得更好的部分**：相较调研中的公开厂商/MCP 示例，本仓库已有版本化 envelope、empty/partial/gap、调用上界、`result_source`、事实路径、HTTP receipt、方向性 drift 和无 raw fallback 的治理组合；不能因为外部产品名气更大而退回只有“成功/失败”的薄合同。
- **评测已经更强的部分**：相较多数公开 OSS benchmark，本仓库的加密受保护 split、pass^4、安全第五层和失败原因台账更接近真实防过拟合评测。开发集目录 LLM 结果仍不能冒充这套受保护证据。
- **能力 census 已经更严的部分**：`segment/delete` 调研证明仓库会检查 body/control-flow 语义，而不是只数 URL/path；这比按 OpenAPI path 或工具名宣称覆盖更可信。

同时有两项“已经无意中做了，但比外部成熟做法差”：一是 marker-only 归属模拟了 ownership，却弱于上游账号 owner/identity，故列为 P0-2；二是精确问句 verified query 模拟 saved query，却弱于结构化定义，故列为 P2-2。渐进式发现也已有三层目录，但 12 命令冷启动仍比少量入口的公开做法更繁琐，故列为 P1-1。

## 做完 P0 后仍未解决的距离

P0 完成后，仓库会更容易选到正确能力、能治理更多自己拥有的既有对象，也能组合已登记语义成员；但还不能据此宣称“所有分析完全脱离 Web”已经完成，至少还差：

1. 8 条完全缺失动线所需的安全非空样本、父对象和成功响应合同；P0 不会伪造这些证据。
2. 6 类尚未闭环的服务端导出；它们在 P1-5 完成前仍可能迫使用户回 Web。
3. 冷启动、多步调查和错误恢复的产品化；单个能力存在不等于整个调查旅程足够短且可恢复。
4. 自定义指标 CRUD、metadata 字典/维度表 CRUD、SQL 工作台三项既定排期的真实交付；P0-3 依赖而不替代它们。
5. 目录 LLM 在受保护集上的泛化证据，以及 read→write 效果隔离；在门槛通过前不能把开发集 `325/336` 宣称为生产可靠性。
6. 调用产品自己的业务语义知识库。campaign 语义、组织口径和 tracking binding 按仓库边界属于调用方；SDK 能提供版本化接口与来源链，但不能替每个业务组织发明正确口径。

远程 MCP、Skill 市场、多 agent 和 Web UI 都不在这段“距离”里，因为它们不是完成仓库内数据分析的必要条件。

## 不确定性与停止条件

- 目前不能从安全合同确定哪些写对象族稳定返回 owner/creator/tenant；P0-2 必须逐族取证，不能预报覆盖数量。
- 目前不能从开发集确定目录 LLM 的受保护泛化表现；只有保管者按冻结方案执行后才能决定是否切默认。
- 目前不能确定 8 条缺失动线和 6 类导出何时会出现安全非空样本；没有证据就保留 gap。
- 目前没有两个明确 MCP 消费者，也没有引力原生 AI 的成功合同；两项都不得用市场热度代替证据升档。
- 本规划没有进行生产请求，所有结论来自九份调研、当前仓库和本机已有分支/提交证据。
